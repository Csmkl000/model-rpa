# Model-RPA 实施路线图与架构评审

## 一、架构可行性深度评审

### 1.1 技术栈成熟度分析

| 组件 | 版本 | 成熟度 | 风险等级 | 备注 |
|------|------|--------|----------|------|
| Tauri v2 | 2.x | ⭐⭐⭐⭐ | 中 | 2024年正式发布，生态逐步完善 |
| React 19 | 19.x | ⭐⭐⭐⭐⭐ | 低 | Meta 主推，社区庞大 |
| Bun | 1.x | ⭐⭐⭐ | 中高 | 性能优秀但生态不如 Node.js |
| Stagehand v3 | 3.x | ⭐⭐⭐ | 中 | Browserbase 出品，API 稳定 |
| Playwright | 1.x | ⭐⭐⭐⭐⭐ | 低 | 微软维护，企业级 |
| React Flow | 11.x | ⭐⭐⭐⭐ | 低 | 成熟的 DAG 画布库 |
| SQLite | 3.x | ⭐⭐⭐⭐⭐ | 低 | 嵌入式数据库王者 |

### 1.2 关键技术风险识别

**风险 1：Bun Sidecar 稳定性**
- 问题：Bun 作为 Tauri Sidecar 运行时，跨平台兼容性待验证
- 缓解：保留 Node.js 降级方案，Bun 作为性能优化而非硬依赖

**风险 2：Stagehand v3 API 变更**
- 问题：Stagehand 仍在快速迭代，API 可能 breaking change
- 缓解：封装适配层，隔离核心业务与 Stagehand 直接调用

**风险 3：Chromium 静默分发的法律与技术风险**
- 问题：Chromium 二进制分发需遵守开源协议，下载失败处理复杂
- 缓解：使用官方 Playwright chromium，实现断点续传 + 哈希校验

**风险 4：Tauri Stronghold 跨平台一致性**
- 问题：Windows/macOS/Linux 密钥存储机制差异大
- 缓解：抽象统一接口，平台特定实现隔离

**风险 5：Token 计费系统的准确性**
- 问题：不同模型 Token 计算方式不同，流式响应计费复杂
- 缓解：使用官方 Tokenizer 库，实现服务端二次校验

### 1.3 架构优势确认

✅ **微内核设计**：核心引擎与业务逻辑解耦，便于维护和扩展
✅ **插件化架构**：MCP 协议支持第三方扩展，生态潜力大
✅ **本地优先**：数据不出本机，隐私安全有保障
✅ **渐进式复杂度**：小白和极客都能用，用户覆盖面广

  ├─ 平台检测与版本匹配

### 5.1 优先级建议

### 5.2 技术选型确认

| 决策点 | 推荐方案 | 备选方案 | 理由 |
|--------|----------|----------|------|
| 包管理器 | pnpm | npm/yarn | monorepo 支持好，速度快 |
| 状态管理 | Zustand | Redux/Jotai | 轻量，TypeScript 友好 |
| 表单处理 | React Hook Form | Formik | 性能优秀，Zod 集成好 |
| HTTP 客户端 | ky | axios | 轻量，TypeScript 原生 |
| 日期处理 | dayjs | date-fns | 体积小，API 友好 |
